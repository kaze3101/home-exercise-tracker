# 要件定義書：自主トレ処方・実施記録アプリ

> **注意**：本アプリで扱うデータはすべて架空です。実在の患者・医療機関のデータは一切使用していません。

## 1. 背景・課題

整形外科クリニックの外来リハビリでは、1回20分程度の限られた時間で、治療と運動指導の両方を行う必要がある。現場で次の課題を感じている。

| No. | 課題 |
|---|---|
| 課題① | 指導時間が短く、運動の目的（ストレッチか筋力強化か）や正しい方法・回数・頻度が患者に十分伝わらない。患者がストレッチと筋トレの違いを理解できていない場合がある。 |
| 課題② | 自主トレは指導するだけで、自宅で実際に行えているかをPTが把握できない。 |
| 課題③ | 外来は1回ごとに費用が発生するため、効果を実感できない患者は来院が途絶えやすい（離脱）。 |

## 2. 目的

自主トレの処方内容（種目・目的・回数・頻度）と実施状況を記録・可視化し、**実施率が低下した患者を早期に発見できるようにする。** これにより、PTが次回来院時に声かけや処方の見直しを行えるようにする。

### 期待する効果（本アプリ単体では検証しない）
- 患者の自主トレに対する理解とモチベーションの向上
- 離脱率の低下

## 3. 利用者

| 利用者 | 主な操作 |
|---|---|
| PT | 患者登録、運動メニュー登録、処方、実施状況の確認、アラート確認 |
| 患者 | 実施記録（実施の有無、痛みの程度）の入力、自分の記録の確認 |

※本アプリはデモとして、画面を「PT用」「患者用」に切り替えて操作する。実運用では患者用画面にログイン機能が必要だが、今回は範囲外とする。

## 4. 用語の定義

| 用語 | 定義 |
|---|---|
| 処方 | 患者に対して、ある運動を「週何日・いつから」行うか指定したもの |
| 実施予定日数 | 処方で指定した週あたりの日数（例：週3日なら、直近7日間の予定日数は3） |
| 実施率 | 直近7日間の（実施日数 ÷ 実施予定日数）。1を超える場合は100%とする。患者単位では、処方すべての合計で算出する |
| 実施率低下アラート | 実施率が閾値（初期値50%）未満の患者 |
| NRS | Numeric Rating Scale。痛みを0（なし）〜10（最悪）の整数で表す指標 |
| 運動種別 | ストレッチ／筋力強化／可動域運動／バランス・協調性運動／有酸素運動 |

## 5. 機能要件

| ID | 機能 | 内容 | 優先度 |
|---|---|---|---|
| F-01 | 患者の登録・一覧 | 年齢層、性別、疾患を登録し、一覧表示・検索できる | 必須 |
| F-02 | 運動メニュー登録 | 種目名、**運動種別**、**目的（何のための運動か）**、説明、目安の回数・セット数を登録できる | 必須 |
| F-03 | 処方登録 | 患者に対し、運動、週あたり日数、開始日を指定して処方できる | 必須 |
| F-04 | 実施記録 | 日付、実施の有無、NRS（0〜10）を入力できる | 必須 |
| F-05 | 実施率の推移グラフ | 患者ごとに、週単位の実施率の推移をグラフ表示する | 必須 |
| F-06 | 実施率低下アラート | 直近7日間の実施率が閾値未満の患者を一覧表示する（閾値は設定画面で変更可能） | 加点 |
| F-07 | 痛みと実施率の併記グラフ | NRSの推移と実施率の推移を同じグラフに表示する | 加点 |

### 課題と機能の対応

| 課題 | 対応する機能 |
|---|---|
| 課題① 運動の目的・方法が伝わりにくい | F-02（種別・目的つきの運動メニュー）、F-03（処方）。患者用画面にも種別・目的・回数を表示する |
| 課題② 実施状況が見えない | F-04（実施記録）、F-05（推移グラフ） |
| 課題③ 効果を感じられず離脱する | F-06（低下アラート）、F-07（痛みと実施率の併記） |

## 6. 非機能要件

| 区分 | 内容 |
|---|---|
| データの扱い | 架空データのみを使用する。患者の氏名は保持せず、ID・年齢層・性別・疾患のみとする |
| 入力値チェック | NRSは0〜10の整数のみ受け付ける。日付は未来日を受け付けない。必須項目が空欄の場合は登録できない |
| 操作性 | 主要な操作（記録入力、グラフ表示）は、画面遷移3回以内で行えること |
| 動作環境 | ローカル環境（Python 3.x）で、READMEの手順どおりに起動できること |

## 7. スコープ外（今回は実装しない）

- ログイン認証・権限管理
- スマートフォン向けアプリ化
- 電子カルテとの連携
- 通知機能（メール・プッシュ）
- 実データの取り込み

## 8. 制約・前提

| 項目 | 内容 |
|---|---|
| 言語・フレームワーク | Python、Streamlit |
| データベース | SQLite |
| テスト | pytest（入力値チェック、実施率の計算、アラート判定を対象とする） |
| バージョン管理 | Git / GitHub（機能ごとにブランチを作成） |
| 開発期間 | 4週間 |

## 9. データ設計（概要）

| テーブル | 主な項目 |
|---|---|
| patients | patient_id (PK), age_group, sex, diagnosis, registered_date |
| therapists | therapist_id (PK), display_name |
| exercises | exercise_id (PK), name, **category（運動種別）**, **purpose（目的）**, description, reps, sets |
| prescriptions | prescription_id (PK), patient_id (FK), exercise_id (FK), therapist_id (FK), days_per_week, start_date |
| exercise_logs | log_id (PK), prescription_id (FK), log_date, done_flag, nrs |

※詳細はER図（`docs/er_diagram`）を参照。
